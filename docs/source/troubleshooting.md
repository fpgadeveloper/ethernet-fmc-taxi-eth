# Troubleshooting

## Build failures

Check the following if the project fails to build or generate a bitstream:

1. **Are you using the correct version of Vivado for this version of the repository?**   
   Check the version specified in the Requirements section of the README.md file. Note that this project is regularly updated
   and you may have to refer to an earlier commit of this repo if you are using an older version of Vivado.

2. **Did you initialise the git submodule?**   
   The Taxi MAC sources live in the `submodules/taxi` submodule. If that directory is empty
   (a plain `git clone`, or a ZIP download), Vivado stops with errors like
   `ERROR: [filemgmt 20-1091] file ... submodules/taxi/src/eth/rtl/taxi_eth_mac_1g_rgmii_fifo.sv does not exist`
   or `cannot find module taxi_eth_mac_1g_rgmii_fifo`. Run `git submodule update --init` in the
   repository and build again.

3. **Did you correctly follow the build instructions?**   
   Please check the build instructions carefully as you may have missed a step.

4. **Did you copy/clone the repo into a short directory structure?**   
   Windows doesn't cope well with long directory structures, so copy/clone the repo into a short directory structure such as
   `C:\projects\`. When working in long directory structures, you can get errors relating to missing files, particularly files 
   that are normally generated by Vivado (FIFOs, etc).

## Licensing questions

The design uses no separately-licensed AMD IP, so Vivado should not ask for a license on a board
that the Vivado ML Standard Edition supports. If you see an evaluation-license warning it refers
to the Vivado edition itself (a device the Standard Edition does not cover), not to the design.

The Taxi library is licensed under the **CERN-OHL-S-2.0**, which is strongly reciprocal: shipping
a product that contains a bitstream built from this design obliges you to make the complete
source of the design available under the same license on request. If that does not suit your
product, FPGA Ninja sells a commercial license for Taxi — see
[`submodules/README.md`](https://github.com/fpgadeveloper/ethernet-fmc-taxi-eth/blob/master/submodules/README.md).

## Ports not working

Check the following if you are unable to get the ports working, in the standalone application or
under Linux.

1. **Is the FMC powered? (ZCU104)**   
   VADJ on the ZCU104 is switched on by the FSBL after it reads the FMC's EEPROM, and the stock
   2025.2 FSBL gets that wrong — it never enables VADJ, the Ethernet FMC stays unpowered, no link
   LED lights and every MDIO read returns `0xFFFF`. Both flows of this repository ship a patched
   FSBL: the Yocto BSP applies `zcu104_vadj_fsbl.patch` to `fsbl-firmware`, and the standalone
   platform is built from the patched sources in `EmbeddedSw/lib/sw_apps/zynqmp_fsbl/`. If you
   build an FSBL another way (a plain Vitis platform, a PetaLinux BSP), apply
   `Yocto/bsp/zcu104/meta-user/recipes-bsp/embeddedsw/files/zcu104_vadj_fsbl.patch` to it — see
   [supported carriers](supported_carriers.md#zcu104).

2. **Is the board configured for JTAG, and can the tools see the cable? (KCU105)**   
   The KCU105 target is loaded entirely over JTAG, so DIP switch **SW15** must select the JTAG
   configuration mode: switch 5 **OFF**, switch 6 **ON** (switches 1 to 4 are don't-care). In any
   other mode the FPGA loads a bitstream from the QSPI flash instead and `fpga -f` has no effect.
   Two more things to check when the tools report *no JTAG targets found*: the board's USB-JTAG
   bridge only enumerates once the board is **powered on**, and on Linux the `ftdi_sio` serial
   driver may claim the bridge's channel A — the channel `hw_server` needs. If it has, unbind it:
   ```
   lsusb -d 0403:6014                     # the on-board Digilent FT2232 bridge
   sudo sh -c 'echo <bus>-<port>:1.0 > /sys/bus/usb/drivers/ftdi_sio/unbind'
   ```
   Installing the AMD cable drivers
   (`<Vivado>/data/xicom/cable_drivers/lin64/install_script/install_drivers/install_drivers`, run
   once as root, then replug the USB cable) is the permanent fix. The *other* channel of the
   bridge is a serial port and is meant to stay with `ftdi_sio` — do not unbind that one. Note
   that the KCU105 console is not on this bridge at all: it is the enhanced port of the board's
   CP2105 USB-UART, at **9600 baud** (see [echo server](echo_server.md#uart-settings)).

3. **Is the PHY delay configuration consistent?**   
   The design is built for `rgmii-rxid`: the FPGA delays the transmit clock by 90 degrees
   (`USE_CLK90 = 1` on the MAC cell, so the RGMII TX clock is `gtx_clk90`) and the PHY is told to
   add the receive clock delay, while the receive-side IDELAYs (`RX_IDELAY_PS`) fine-tune the
   data sampling. If you change the PHY mode in software (the lwIP netif or the device tree
   `phy-mode`) without changing the hardware, or vice versa, the link comes up but frames are
   corrupted: the symptom is a link that reports 1000 Mbps while `rx_bad` / `flag_rx_bad_fcs`
   climb in `ethtool -S` (Linux) or the RX_BAD_CNT register (standalone) and nothing is received.

4. **Check the interface-to-port assignment (Linux)**   
   The `eth<N>` interface numbers do not track the FMC port numbers (they depend on probe
   order; the board's own RJ45 is `end0`). Identify the ports by MAC address
   (`00:0a:35:06:21:05`–`:08` = ports 0–3) or by driver (`ethtool -i eth1` shows `taxi_mac`) —
   see [Yocto](yocto.md#identifying-the-ports).

5. **Each port must be assigned to a different subnet (Linux)**   
   If you assign interface eth1 to IP address 192.168.1.10, then you must use a different subnet for the IP address of eth2, eth3 and eth4.
   Multiple ports that are managed under Linux must be assigned to different subnets, or they will not work.
   An example address assignment would be eth1=192.168.1.10, eth2=192.168.2.10, eth3=192.168.3.10, eth4=192.168.4.10.
   (The standalone echo server is different: lwIP answers on the interface a frame arrived on, so
   its four ports deliberately share one subnet.)

6. **Is the `taxi_mac` module loaded (Linux)?**   
   `lsmod | grep taxi_mac` should list it and `dmesg | grep taxi` should show one probe line per
   port. If the driver warns that `xlnx,irq-delay` is missing on the S2MM channel, receive latency
   will be very poor: the device tree needs the property described in
   [`Linux/taxi-mac/README.md`](https://github.com/fpgadeveloper/ethernet-fmc-taxi-eth/blob/master/Linux/taxi-mac/README.md).

## Yocto issues

### Yocto build fails with sstate fetch errors

If a `./build.sh yocto --target <board>` run ends with errors like

```
ERROR: <package>-<ver>-r0 do_..._setscene: Fetcher failure: Unable to find file file://.../sstate:...
```

the actual build is not broken. The `_setscene` errors come from bitbake
trying to pull prebuilt artifacts from the public AMD sstate-cache mirror,
which occasionally returns 404 for individual packages. Bitbake then falls
back to building those packages locally — **re-run the same command**; the
second attempt finds the missing packages in the local sstate cache (populated
by the first run) and completes cleanly. To make builds independent of the
public mirror, point the build at a local sstate mirror
([Yocto offline build](build_instructions.md#yocto-offline-build)).

### The board does not boot from the SD card

The EDF wic image does not put `BOOT.BIN` where the BootROM looks for it. Copy `BOOT.BIN` onto the
first FAT partition (`esp`) by hand after flashing the image — step 4 of
[prepare the SD card](yocto.md#prepare-the-sd-card) — and check the boot-mode switches
(ZCU104: SW6 = `1000`).

## Dropped pings/packets

No dropped packets are to be expected with our example designs. If you are experiencing dropped packets of any kind, this can be an indication
of one of the following issues:

* Timing in the FPGA design is not optimal (check for timing errors in the Vivado design)
* Timing of the RGMII interface is not optimal (can be due to the FPGA design, the IDELAY value or the PHY delay configuration — see above)
* Under Linux, the MAC has no address filter, so on a busy network every frame on the wire is
  delivered to the kernel; `rx_fifo_ovf` in `ethtool -S` climbing under load means the receive
  path cannot keep up with the traffic on that segment.

We ensure that there are no timing errors or issues on all of our designs before making a release, so typically this problem occurs on
custom designs where the timing issues have not yet been optimized. Please [contact us](https://opsero.com/contact-us/) for support 
if you are experiencing dropped packets.
